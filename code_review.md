# Kernel‑Eye: Engineering Code Review & Production‑Hardening Guide

> **Project goal**: Use BPF LSM hooks to protect critical files (`/etc/shadow`, `/etc/sudoers`, SSH keys, etc.) and make the monitoring agent resilient to tampering (signal‑delivery, ptrace).  
> **Current commit history** (from initial to latest):
> - `d6eca56` – hardened `task_kill`, enlarged ring buffer to 512 KiB.
> - `d860497` – added `ptrace_access_check` LSM hook.

## 1. Architecture Overview

```
┌─────────────────────────────┐
│  User‑space daemon          │
│  (kernel-eye/src/main.rs)   │
│                             │
│  • Reads ring buffer        │
│  • Populates maps           │
│  • Prints JSON events       │
└──────────┬──────────────────┘
           │
           │  aya Ebpf load / attach
           ▼
┌──────────────────────────────────┐
│  BPF programme                   │
│  (kernel-eye-ebpf/src/main.rs)   │
│                                  │
│  LSM hooks:                     │
│  • file_open                     │
│  • task_kill                     │
│  • ptrace_access_check           │
│  • task_free   (clean‑up)        │
└──────┬───────────────────────────┘
       │
       │  BTF‑typed arguments (verifier)
       ▼
   Kernel internals
```

- **Shared data** (`kernel-eye-common`) defines `EventData` and constants (event types, actions) – used by both BPF and user‑space.
- **Bindings** (`kernel-eye-ebpf/src/bindings.rs`) are auto‑generated by `bindgen` from a specific `vmlinux.h`; they provide the layouts of `struct file`, `inode`, `task_struct`, etc. that the BPF code accesses directly.

## 2. What Has Been Improved So Far

| Area | Change | Benefit |
|------|--------|---------|
| Anti‑tamper (`task_kill`) | Blocks **all** signals to the agent (not only SIGKILL/SIGTERM) | Harder to kill the daemon |
| Ring buffer size | Increased from 256 KiB to 512 KiB | Lower chance of event drops under load |
| Anti‑tamper (`ptrace`) | New LSM hook `ptrace_access_check` blocks any non‑agent process from tracing the agent | Prevents debugger‑based attacks |

## 3. Detailed Findings & Remaining Issues

### 3.1 eBPF Program (`kernel-eye-ebpf/src/main.rs`)

#### 3.1.1 Structural Risks
- **BTF layout dependency**: The code dereferences fields like `(*fp).f_inode`, `(*inode_ptr).i_ino`, `(*target).tgid`.  These offsets come from `bindings.rs` which was generated against a **specific kernel**.  If the running kernel differs (e.g., different config, distro‑backported patches, different KABI), the verifier may reject the program or, worse, access wrong data.  
  *Mitigation*: Regenerate `bindings.rs` for the exact target kernel (run `bindgen` against that kernel’s `vmlinux.h`).  Add a runtime check in user‑space that compares `uname -r` with the expected version.

- **Missing return‑value checks**: Both `PROTECTED_INODES.get(&ino)` and `WHITELIST_PIDS.get(&tgid)` are called inside `unsafe` blocks.  The map lookups are allowed by the verifier, but if the map is not pre‑loaded or becomes full, a lookup can fail (return `None`).  The current logic treats `None` as “not found”, which is usually correct, but there is no handling for a full map (new entries will be rejected).  This is fine for a fixed set, but you should guarantee that the userspace always populates all entries before starting the event loop.

#### 3.1.2 Security Gaps
- **No protection against `process_vm_readv` / `process_vm_writev`**.  A root attacker can still read/write the agent’s memory without going through ptrace.  Adding a `process_vm_writev` (or the newer `bpf_lsm_process_vm_rw`) hook would close this gap.  For now, the agent’s memory is not protected from direct cross‑process access.
- **No hook for `path_unlink` / `path_rename`**.  A privileged process can rename `/etc/shadow` to `/etc/shadow.bak`, create a new file with the same inode (or steal the inode), and bypass the `file_open` check.  The LSM `path_unlink` and `path_rename` hooks are not yet implemented.
- **No hook for `file_permission` or `inode_permission`**.  Currently only `file_open` is checked.  If a file is already open (e.g., via an existing fd), further reads/writes are not inspected.  Consider adding `file_permission` or `inode_permission` hooks.

#### 3.1.3 Event Emission
- `emit_event` calls `EVENTS.output::<EventData>` but ignores the return value.  If the ring buffer is full, events are silently dropped.  For critical tamper events (`EVENT_TAMPER + ACTION_BLOCKED`), you may want to store a counter in a shared BPF map (e.g., a percpu array) so the user‑space can query total blocked attempts.  This also helps forensic analysis.

### 3.2 User‑space Daemon (`kernel-eye/src/main.rs`)

- **No graceful shutdown of LSM hooks**: The `break` on Ctrl‑C simply exits the loop.  The loaded LSM programs stay attached **forever** (the `Ebpf` object is leaked).  This is acceptable because the agent is intended to run until reboot, but if you ever need to unload the BPF programs (e.g., for upgrade), you’ll need to implement an explicit detach/cleanup path.  The current behaviour prevents double‑loading if the daemon is restarted.
- **Hard‑coded list of protected files**: `PROTECTED_PATHS` is a compile‑time constant.  For a dynamic environment, consider reading the list from a configuration file (or an eBPF map that the admin can update at runtime).
- **No PID re‑use mitigation**: When the agent restarts, its PID might be immediately reused.  Since the `task_free` hook removes the old PID from `WHITELIST_PIDS`, and the new agent inserts its own PID, there is a tiny race window where a newly‑born process could inherit the old PID and be whitelisted before the new agent inserts itself.  The probability is low, but you can eliminate it by using a unique token (e.g., a random 64‑bit ID stored in a dedicated BPF map) instead of relying solely on PID.
- **Logging**: currently prints JSON to stdout.  For production, forward logs to `journald` or a SIEM collector.  Consider using a structured logging framework (e.g., `tracing`) with a JSON layer.

### 3.3 Common Crate (`kernel-eye-common/src/lib.rs`)

- `EventData` is `#[repr(C)]` and uses fixed‑size arrays, which is safe for cross‑boundary access.  The `unsafe impl aya::Pod` is conditionally compiled, which is correct.
- The crate is `#![no_std]`, allowing it to be shared between BPF and user‑space.  No changes needed.

## 4. Verifier & Kernel Environment Notes

- The BPF LSM hooks are **BTF‑typed**, meaning the verifier can follow pointers into kernel structures.  However, it still enforces that all accessed fields are within the bounds of the structure **at load time**.  The program will load successfully only if the offsets in `bindings.rs` match the BTF info from the running kernel.
- The ring buffer size is limited by the maximum allowed allocation for `BPF_MAP_TYPE_RINGBUF`.  Most kernels cap this at 256 KiB default; we increased it to 512 KiB, which should work on modern kernels with `CONFIG_BPF_RINGBUF_SIZE_512K` enabled.  If deployment kernel supports only 256 KiB, you’ll need to adjust.

## 5. Recommendations for Production Readiness

### 5.1 Immediate “Next Steps”

1. **Regenerate bindings for the target kernel** and verify loading.
2. **Test the hardened `task_kill`** against `kill -9`, `kill -15`, `pkill`, `sysrq` (if enabled), and **SIGSTOP** (some kernels allow LSM to block SIGSTOP, but not all – test).
3. **Test `ptrace_access_check`** with `strace -p`, `gdb attach`, and `ptrace` from a non‑root process.
4. **Monitor ring buffer drops**: add a counter in BPF (percpu array) for each event type, and expose it via a separate BPF map that user‑space can read periodically.
5. **Add a `file_rename`/`path_unlink` LSM hook** to prevent inode recycling attacks.  For `file_rename`, you need to check both the old and new inode; for `path_unlink`, deny if the inode is protected.
6. **Add a `process_vm_rw` hook** (if available) or at least `mmap_file` / `mmap_addr` checks to prevent memory injection.

### 5.2 Long‑term Architectural Improvements

- **Multi‑agent coordination**: If you run multiple instances, the `WHITELIST_PIDS` map will conflict.  Implement per‑instance maps or a BPF‑based identity token.
- **BPF‑based heartbeat / watchdog**: A periodic BPF kprobe on `sys_sync` (or a custom tracepoint) could detect if the userspace daemon has died and trigger a restart (e.g., via `uevent` or a separate supervisor).
- **Policy engine**: Instead of hard‑coding file lists, implement a BPF map that stores rules (inode, allowed‑UIDs, allowed‑groups, etc.) that can be updated from user‑space without restarting the daemon.
- **Audit log enrichment**: Include the parent PID and the executable path in events to improve forensic value.
- **Integration with container runtimes**: If the agent runs inside containers, ensure that PID namespaces and mount namespaces are handled correctly.  The current code uses host‑level TGID, which may not match the container’s PID namespace.

## 7. Conclusion

Kernel‑Eye has moved from a basic file‑guard prototype to a more resilient system by blocking arbitrary signal delivery and preventing ptrace.  The next milestones should focus on closing the remaining attack vectors (file rename, memory injection) and improving operational robustness (bindings verification, drop counters, dynamic configuration).  With these additions, the project can be confidently deployed in production environments as a last‑line file‑integrity monitor.
